# 数据模型与离线一致性 需求规格说明

> 状态：已确认
> 创建日期：2026-08-03
> 所属里程碑：M2-M3（横切基础设施）

## 1. 概述

### 1.1 功能简述
定义双端本地数据持久化模型，并保证双端在离线、重连、重装等场景下收敛到一致状态。原则：**轻游戏化标准，事件驱动 + 时间戳合并，不追求银行级强一致**。

### 1.2 所属模块
本地 SQLite 数据库（`06-数据模型` schema）、`sync/queue.py`（去重与离线队列）、`core` 各模块的持久化读写。

## 2. 用户故事与场景

### 2.1 目标用户
已配对的情侣双方及其设备。涉及换机/重装的用户。

### 2.2 用户故事
- 作为用户，我希望断网时操作不丢失，以便恢复后数据自动补全。
- 作为用户，我希望重装/换机后我的团子状态还能找回，以便不从头再来。
- 作为用户，我希望网络重试不会导致消息重复，以便体验整洁。

### 2.3 使用场景
1. **离线重连补发**：A 断网期间的带话与积分事件，联网后自动按序补发，双方一致。
2. **网络重试去重**：同一事件因网络抖动重试两次，接收端只处理一次。
3. **换机恢复**：A 换电脑，重新配对后从 B 端导出备份导入，团子等级/亲密度/装扮恢复。

## 3. 功能需求

### 3.1 输入
- 各类业务事件（带话、情绪、积分、装扮解锁、纪念日）。
- 用户操作：换机恢复导入、手动同步触发。
- 系统事件：连接恢复、每日零点对齐。

### 3.2 输出
- 持久化数据（配对、事件日志、带话、礼物、养成状态、纪念日）。
- 一致性校验结果（成功 / 差异已修复 / 异常需人工）。
- 恢复导入结果。

### 3.3 核心行为描述
1. **本地数据模型**：使用 SQLite 存储六类数据——配对与密钥、事件日志、带话记录、用户物品与礼物发送记录（`gift_offers` / `user_items`）、养成状态、纪念日。事件日志记录全局唯一事件标识用于去重与审计。
2. **密钥存储安全**：会话密钥加密后落盘（Windows DPAPI / Linux SecretService；兜底为受限权限文件），私钥权限严格受限。
3. **事件去重**：每个事件以"发送方标识 + 序号"构成全局唯一标识；接收时先查事件日志，已存在则丢弃，否则写入并投递（幂等）。
4. **离线队列与重试**：发送侧网络不可用将事件入队，按序号升序补发；带过期时间的事件超时标记失败。接收侧离线暂存由中继负责（TTL 7 天）。
5. **事件日志清理**：`events` 表仅保留去重与补发所需的近期记录——已确认（`acked_at` 非空）或对应业务已判失败（带话过期、礼物过期等）且超过保留期（默认 90 天）的记录删除；仍在去重/补发窗口内（保留期内、或未确认未过期）的记录不清理。清理在启动时与每日零点各执行一次，分批删除（每批 1000 行）避免长事务；仅清理 `events` 表，业务表（`carries` / `gift_offers` / `user_items` / `pet_state` / `anniversaries`）不参与。
6. **冲突合并**：通用规则为"最新时间戳为准"；不同键各自保留；一次性事件（如装扮解锁）以接受事件为准；亲密度不从数字同步，而是从带签名的积分事件流重放收敛。
7. **防作弊**：每个积分事件带签名（会话密钥派生），并受每日原因上限约束；签名非法或超限则拒绝合入。
8. **每日兜底对齐**：每日零点通过一次 `date.sync` 对齐事件校准共同登录天数等累计数据，差异以事件日志修复。
9. **换机/重装恢复**：重新配对获取新密钥；数据恢复来源为对方端"导出备份"（本地导入）或可选的密文备份；恢复后以备份快照 + 对方端现存近期事件为准对齐，不依赖已清理的历史日志（清理边界见第 5 条事件日志清理）。

### 3.4 业务规则与约束
- 同一事件只处理一次（幂等去重）。
- 事件日志清理不删除仍在去重/补发窗口内（保留期内、或未确认未过期）的记录。
- 短时不一致（秒级）可接受；长期不一致由每日对齐兜底。
- 重大异常（签名连续失败、重放溢出）时停止自动合入并提示用户手动同步。
- 备份必须为密文（**用户口令派生密钥加密**，scrypt 派生后经 SecretBox 加密），中继不可解；口令由用户自行保管，遗忘则无法恢复。

## 4. 非功能需求

### 4.1 性能要求
- 事件去重与写入 < 10ms。
- 每日对齐与全量核对不阻塞主线程，峰值 < 100ms。
- `events` 表规模有界：清理已确认/已过期失败且超过保留期（90 天）的事件，数据库文件保持可控（见 3.3 事件日志清理）。

### 4.2 安全要求
- 事件日志明文仅存本端；外发一律密文。
- 密钥与备份加密存储。

### 4.3 兼容性要求
- SQLite 为内嵌数据库，无需外部服务。
- 数据模型版本化，schema 变更走迁移（自研轻量版本表：`schema_version` 表 + `migrations/NNN_*.sql` 顺序脚本，启动时按序执行未应用的版本）。

## 5. 边界与限制

### 5.1 明确包含（In Scope）
- 六类本地数据表的定义与访问。
- 密钥加密落盘。
- 事件去重、离线队列、重试、过期。
- LWW 合并、亲密度事件重放、签名校验、每日对齐。
- 换机/重装恢复（对方导出或密文备份）。

### 5.2 明确排除（Out of Scope）
- 银行级强一致/分布式事务。
- 服务端数据库或云同步（中继仅暂存密文）。
- 多人协作或群组状态。

### 5.3 已知约束
- 最终一致而非强一致，存在秒级不一致窗口。
- 防作弊为尽力而为，无法防止双方共谋的合理互动。
- 当前按"一人一端"设计，多设备并发在线不在此范围。

## 6. 验收标准（Acceptance Criteria）

- **Given** 接收端收到事件；**When** 该事件标识已存在；**Then** 丢弃不投递，避免重复。
- **Given** 发送侧断网；**When** 产生多个事件；**Then** 事件按序入队，联网后按序号升序补发，未过期的均成功送达。
- **Given** 双方离线各自产生积分；**When** 恢复联网；**Then** 从事件流重放后亲密度一致。
- **Given** 一方签名非法的积分事件；**When** 接收端校验；**Then** 拒绝合入并提示。
- **Given** 用户换机重装；**When** 导入对方导出的备份；**Then** 团子等级、亲密度、装扮、纪念日均恢复。
- **Given** 每日零点；**When** 对齐事件执行；**Then** 共同登录天数等累计数据双方校准一致。
