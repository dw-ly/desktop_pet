# 数据模型与离线一致性 实施计划

> 关联 Spec：[[7-AI学习/11-AI桌宠情侣互联/spec/data-consistency/spec.md|spec/data-consistency]]
> 创建日期：2026-08-03
> 状态：已确认

## 1. 技术方案概述

data-consistency 是**横切基础设施**（M2-M3），为双端提供统一持久化模型与离线收敛机制。原则：**轻游戏化标准，事件驱动 + 时间戳合并，不追求银行级强一致**。职责分五块：① 本地 SQLite 六类表 schema 与版本化迁移；② 事件去重与离线队列（收编 sync-security M2 的 queue 自带 schema 并入 `events` 表）；③ 事件日志清理（90 天保留 / 分批删除 / 仅动 events 表）；④ 冲突合并（LWW + 签名积分事件流重放 + 每日原因上限）；⑤ 换机/重装恢复（口令加密备份导出/导入）。

数据库层运行在 Core 侧，供各业务模块读写；去重与队列逻辑被同步线程调用。关键衔接：**G1（schema 基线 + 迁移框架）是"地基中的地基"**——若按开发顺序 carry-message 先行，其 `carries` 表先内联建表、本模块落地时统一纳入 migrations（与 sync-security queue 相同策略）；实施上建议将本模块批次 1 提前到 carry-message 之前。

## 2. 技术决策

### 2.1 方案选型

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 数据库 | SQLite（Python 标准库 `sqlite3`） | spec 已定；内嵌免部署，兼容性 §4.3 要求 |
| schema 版本化 | 自研轻量版本表：`schema_version` + `migrations/NNN_*.sql` 顺序脚本，启动时按序执行未应用版本，事务内执行失败回滚 | spec 决议；无外部迁移工具依赖 |
| 去重键 | `event_id = "{from}:{seq}"` 全局唯一 | spec 已定；幂等去重 |
| 离线队列 | **统一并入 `events` 表**（收编 sync-security M2 queue 自带 schema），以状态字段区分 pending/sent | sync-security plan 已声明；消除双 schema 冲突 |
| 事件日志清理 | 保留期 90 天；启动时 + 每日零点触发；每批 1000 行；**仅清理 events 表** | spec 决议；避免长事务锁库 |
| 冲突合并 | LWW（最新时间戳为准）+ 不同键各自保留 + 一次性事件（装扮解锁）以 accept 事件为准 | spec 已定 |
| 亲密度一致性 | **不直接同步数字**，从带签名积分事件流重放收敛 | spec 已定；防作弊 + 两端一致 |
| 防作弊 | 每积分事件带 HMAC 签名（会话密钥 HKDF 派生**独立 MAC 子密钥**）+ 每日各 reason 上限 | spec 已定；密钥分离最佳实践 |
| 每日对齐 | 每日零点发 `date.sync` 全量核对累计数据，差异以事件日志修复 | spec 已定 |
| 备份加密 | **用户口令派生密钥**（PyNaCl `pwhash.scrypt` → SecretBox 加密），独立于配对状态 | 用户决议；换机重新配对后旧会话密钥失效，会话密钥派生会导致旧备份无法解密；口令派生任何时刻可解 |
| 签名密钥与加密密钥 | 会话密钥经 HKDF 派生独立子密钥（MAC 子密钥 / 加密子密钥分离） | 密钥分离；sync crypto 提供派生能力 |

### 2.2 外部依赖

| 依赖 | 用途 | 新增 |
|------|------|:---:|
| SQLite（`sqlite3` 标准库） | 本地持久化 | 无（标准库） |
| 同步层 crypto（`pynacl`） | 会话密钥派生（HKDF）、SecretBox 加解密、HMAC 签名、scrypt 口令派生 | 复用 |
| keyring（同步层已引入） | 备份口令不入 keyring（仅用户记忆），无新增用途 | 无 |

### 2.3 内部依赖

- **事件注册表**：`events.type` 枚举来自 sync-security 注册表（唯一登记处）；`date.sync` 已登记，本模块消费。
- **同步层 queue**：收编其 M2 自带 schema 到 `events` 表；发送补发、接收去重逻辑迁至本模块统一实现。
- **同步层 manager**：连接状态查询（补发时机、对齐可用性）、发送 `date.sync` 事件、注册接收 handler。
- **业务模块**：`carries` / `gift_offers` / `user_items` / `pet_state` / `anniversaries` 表 schema 由本模块定义（0001 基线），各业务模块提供读写封装（如 carry_store.py）；若业务模块先行实施，则其表先内联、本模块落地时统一并入 migrations。
- **配置**：data_dir（运行时数据目录 `~/.tuanzi/`）、保留期（90 天）、分批大小（1000）、清理触发（启动 + 每日零点）、备份口令强度提示阈值。

## 5. 测试标准

### 5.1 单元测试标准

- **迁移**：空库初始化、增量脚本、脚本失败回滚、重复执行幂等。
- **去重**：重复 `event_id` 丢弃；不同发送方同序号不冲突；插入与投递原子。
- **离线队列**：入队 / 按序补发 / 过期标记 failed / 原队列表数据迁移。
- **事件清理**：保留期边界（未到 / 恰到 / 已过）；分批每批 ≤1000 行；仅 events 表；业务已判失败纳入清理。
- **冲突合并**：LWW 同键取最新 ts；不同键各自保留；一次性事件不覆盖。
- **亲密度重放**：双端一致收敛；签名非法拒绝；每日上限拒绝；连续异常停止合入。
- **备份**：口令加密导出/导入往返一致；错误口令失败；换机重配对后旧备份可解。

### 5.2 集成 / 场景验证标准

- **前置条件**：sync-security 联调通过（plan/sync-security 验收完成），双端配对在线。
- **步骤**：双端互发事件 → 重试投递不重复 → 断网产生多事件 → 重连按序补发 → 双方各自产生积分 → 重放后亲密度一致 → 每日零点对齐 → 清理运行且 events 表有界 → A 导出备份 → 新 data_dir 重新配对（模拟换机）→ 导入恢复 → 团子等级/亲密度/装扮/纪念日完整 → 与对方端对齐。
- **期望结果**：去重、补发、重放、对齐、清理、恢复全链路正确，数据库文件可控。
- **异常场景**：重复投递、过期事件、签名非法积分、错误备份口令、断网时对齐推迟、迁移中途失败。

## 6. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| events 表清理后超期重放导致重复投递 | 接收端重复处理历史事件 | 保留期 90 天远大于任何重试窗口；超期重放属异常场景（spec 已接受）；清理跳过未确认未过期记录 |
| 亲密度重放依赖事件流完整 | 历史事件清理后重放缺口 | 换机恢复走备份快照 + 对方端近期事件对齐，不依赖已清理日志（spec 已决议） |
| 备份口令遗忘 | 数据无法恢复 | 导入/导出时口令强度提示 + 文档强调口令务必自行保管；口令不入 keyring、不存盘 |
| 清理与补发并发 | 误删在途事件 | 清理条件强制"保留期内不删 + 未确认未过期不删"；补发队列事件状态为 pending/sent 时不被清理 |
| 每日对齐与本地修改冲突 | 短暂不一致 | 以事件日志为准修复；秒级不一致可接受（spec §3.4） |
| 迁移脚本失败 | 应用无法启动 | 事务回滚 + 明确提示，不启动应用；迁移脚本先单测再发布 |
| 业务模块先行造成表结构偏差 | 统一迁移成本 | G1 建议前置；业务模块先行时按 sync queue 同款"内联后统一"策略收口 |
